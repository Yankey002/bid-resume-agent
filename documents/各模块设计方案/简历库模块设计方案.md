# 简历库模块设计方案 (V2.1)

## 1. 概述
本方案旨在构建一个以“候选人”为核心的智能化简历管理系统。相比 V1.0 的单纯文件列表模式，V2.0 引入了“候选人档案”概念，通过大模型辅助提取姓名，自动建立人与文件的关联。核心目标是实现“以人管档”，解决重名问题，并提供高效的浏览与归档体验。

## 2. 核心架构变更

### 2.1 数据模型：引入候选人 (Candidate)
不再仅存储孤立的文件记录，而是建立 `Candidate` (候选人) -> `Resume` (简历文件) 的 1:N 关系。

*   **Candidate (候选人)**
    *   `id`: UUID (主键)
    *   `unique_id`: String (6位数字编号，如 `000001`)，用于前端展示和区分重名用户。
    *   `name`: String (候选人姓名)
    *   `created_at`: Timestamp
    *   `updated_at`: Timestamp
*   **RawResume (原始简历)**
    *   ...原有字段...
    *   `candidate_id`: UUID (外键，关联 Candidate)

### 2.2 唯一标识策略 (Updated)
*   **重名处理**：系统允许同名 `name` 存在。
*   **生成规则**：采用**顺序递增**策略（Sequential）。
    *   起始编号：`000001`
    *   增长规则：每次创建新候选人时，查询当前最大 ID 并 +1。
    *   并发处理：前端支持批量导入时的 ID 预分配（本地递增预览），后端具备冲突检测与自动重试机制，确保 ID 唯一且连续。
*   **展示方式**：前端始终以 `姓名 (ID: 000001)` 的形式展示，确保无歧义。

## 3. 业务流程设计

### 3.1 页面布局 (Master-Detail)
摒弃传统的单一表格视图，采用左右分栏设计：

*   **左侧侧边栏 (Sidebar)**：候选人导航
    *   **搜索框**：支持按姓名或 6 位 ID 搜索。
    *   **列表项**：显示候选人姓名、ID、最新更新时间。支持**多选**与**批量删除**。
*   **右侧主内容区 (Main Content)**：档案详情
    *   **头部**：候选人基本信息（姓名、ID）。
    *   **文件归档区**：折叠面板/列表，显示该候选人名下的所有历史简历文件。
    *   **操作区**：预览、下载、删除文件。

### 3.2 智能导入流程 (V2.1 Implemented)
导入流程升级为“识别-确认-归档”三步走，重点优化了自动化体验。

1.  **上传与识别**：
    *   用户选择文件 -> 前端调用 LLM 接口提取姓名。
2.  **智能匹配与消歧 (关键步骤)**：
    *   前端拿到姓名后，查询后端是否存在同名候选人。
    *   **场景 A：无同名** -> **自动选中**“新建候选人”。
        *   系统预分配下一个可用 ID（如 `000005`），若同时导入多人，前端自动递增显示（`000005`, `000006`...）。
    *   **场景 B：仅有 1 个同名** -> **自动选中**该候选人。
        *   界面显示归档选项，不弹出警告，实现“零点击”归档。
    *   **场景 C：有 >1 个同名** -> **不自动选中**。
        *   界面显示**黄色警告**，列出所有同名候选人（附带 ID 和已有文件数），强制用户手动选择。
3.  **用户确认**：
    *   用户仅需处理“多重匹配”的冲突项，其他项可直接通过。
4.  **最终归档**：
    *   提交时携带确认后的 `candidate_id`（或新建标记）及预分配的 ID。

## 4. 前端设计 (Frontend)

### 4.1 组件重构
*   **`ResumePage`**: 采用 `Layout` 布局。
*   **`CandidateList`**: 支持虚拟滚动、复选框多选、批量删除确认弹窗。
*   **`ImportResumeModal`**:
    *   集成 `IdentitySelector` 逻辑。
    *   实现前端 ID 智能自增逻辑 (`lastSuggestedIdRef`)。
    *   实现自动归档策略（单匹配自动选，多匹配强制选）。

### 4.2 交互细节
*   导入时实时显示建议 ID，让用户心里有数。
*   删除候选人时，弹出红色警示，明确告知将**级联删除**所有关联的简历文件。

## 5. 后端设计 (Backend)

### 5.1 数据库变更
*   `candidates` 表：`unique_id` 字段索引且唯一。
*   `raw_resumes` 表：级联删除配置 (`cascade="all, delete-orphan"`)。

### 5.2 API 扩展
*   `GET /api/candidates/suggest-id`: 获取下一个可用 ID。
*   `POST /api/candidates`: 创建接口，支持传入 `unique_id`。若冲突，后端自动重试生成新 ID。
*   `DELETE /api/candidates/batch`: **批量删除接口**。
    *   逻辑：先查询出所有关联的 `RawResume` -> 收集物理文件路径 -> 删除 DB 记录 (级联删除) -> **同步删除物理文件**。
    *   日志：输出详细的删除统计。
